1. なぜ「測る」のか

座標を出す道具は世に多い。足りないのは出した配置が読めるかを測る道具で、そこが実際に事故を生む。 下は実際に起きた欠陥の再現。左が壊れていた版、右が直した版。データも設定も同じ。

fitText が返した「…」が常に円の内側に収まってしまい、外周 8 方向を一度も試さなかった。 すごろくゲーム tetsugo の 616 駅が全部「…」になり、しかも measure() はそれを「問題なし」と報告した。 他人の図を検査する道具が、自分の配置で同じ間違いをしていた。

2. 壊してみる

幅を縮めると、何がどう壊れるかが数値で出る。メッセージには必ず実測値・閾値・直し方が入る — 読むのが人でも LLM でも、メッセージだけを見て直せなければ意味がないから。

3. 配置

同じデータを 3 通りに置く。どれも同じ入力からは必ず同じ座標が出る（決定論的）。

手牌やツールバーのように順番が意味を持つものは、押し離しでは並べられない（順序が壊れる）。 grid は入りきらない量を overflow で返すだけで、勝手に縮めない。

4. 押し出して消すのは解決ではない

領域の外へ押し出せば重なりは必ず消える。だがそれは解決ではない。 麻雀ゲーム netmahg で手牌を押し離したら重なりは 0 になったが、幅が 543px に再拡大して画面に入らなくなった。

5. 3D で新しく問題になる 3 つ

2D の指標をそのまま持ち込んでも測れないものがある。どれも視点を与えないと測れないので、 measure3 は camera を取る。

遮蔽（手前の物が奥を隠す）· 通行（人が歩くなら隙間が狭いと通れない）· 距離による可読性（ラベルの大きさは距離で決まる）。 投影は project() が純粋な数式でやっている — three.js も WebGL も使っていない。

6. 実地で見つかった欠陥

このエンジンが良くなったのは、全部実際のプロダクトに当てて批判されたから。
